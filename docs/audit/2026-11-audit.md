# Technical and security audit: com_servicedeskplus 1.32.5 → 1.33.0

Date: 2026-11-23. Scope: the whole repository (component code, templates, assets, SQL, install script, build scripts, release workflow, documentation).

## 1. Executive summary

`com_servicedeskplus` is a Joomla 6 component that gives employees a self-service portal to ManageEngine ServiceDesk Plus On-Premises. It covers requests, approvals, loans, announcements and a dashboard. One technician API key is used for every user, so the component itself must make sure that each user sees and changes only their own ServiceDesk Plus records.

**The codebase is in good condition.**
- Core logic is separated from Joomla behind interfaces (transport, repositories, cache, audit).
- No deprecated Joomla APIs are used.
- Output escaping, CSRF tokens, ACL checks and server-side ownership checks are present on every page and action reviewed.
- The API key is encrypted with AES-256-GCM.

**Findings:**
- **Critical or High security issues:** none.
- **Medium security issue (fixed):** a gap in the 1.31.6 "API technician can't be linked" protection. Links made before 1.31.6 were not covered.
- **High performance issues:** two. One is fixed: request pages are now read in parallel. The other, the approvals scan, is documented and left open.
- **Medium and Low issues:** several, covering security, standards, performance, accessibility and RTL. Most are fixed.

**Testing:** the repository had no automated tests. There are now 76 PHPUnit tests, and they run in CI.

**One known risk is accepted by the owner and not changed:** new users matched by e-mail are approved automatically (the default). See section 10.

## 2. Architecture assessment

| Area | Assessment |
|---|---|
| Structure | Standard Joomla 6 component. Namespace `SdpPortal\Component\ServiceDeskPlus`, service provider with `MVCFactory`, `ComponentDispatcherFactory` and `RouterFactory`, `MVCComponent` with `RouterServiceInterface`, and a `RouterView` router with numeric segment checks. |
| Separation of concerns | Good. About 70 of 147 PHP classes have no Joomla dependency: the API client, services, value objects and security classes. They use injected interfaces (`TransportInterface`, `UserMapRepositoryInterface`, `UserCacheInterface`, `AuditLogInterface`, PSR-3 logger). Controllers and views are thin. |
| Data | Four tables: `#__sdp_settings`, `#__sdp_user_map` (unique `sdp_user_id`), `#__sdp_cache` (per Joomla user and SDP user) and `#__sdp_audit`. MySQL and PostgreSQL schemas and update files are consistent from 1.0.0 onwards. |
| Integration | ServiceDesk Plus REST API v3 through `SdpClient`: path allow-list, numeric ids, no redirects, TLS verification or key pinning, parallel GETs over a shared cURL handle, and errors mapped to kinds. |
| Error handling and logging | `SdpException` kinds map to user language strings. Site users never see ServiceDesk Plus texts. Logs are scrubbed of keys by `Redactor`. |
| Large classes | `ApprovalService` (about 1,350 lines) mixes reading approvals with the decision workflow. A split into a reader and a decider is justified, but it was **not done** in this audit, to avoid risk to the approval flow without integration tests against a live server. `SdpClient` (about 1,250 lines) is a wire layer plus thin endpoint methods; splitting it is optional. |

## 5. Security assessment

### Findings and remediation

**S1 – Medium – API technician check only used the Joomla e-mail (fixed).**
- **Affected:**
  - `IdentityResolver::doResolve`
  - `ApprovalService::listPending`
  - `ApprovalService::locateOwn`
- **Impact:** some portal users were linked to the API technician's ServiceDesk Plus user but have a different Joomla e-mail. Examples: links made by an administrator before 1.31.6, or before that technician was chosen. These users could see that account's pending entries and decide them, including entries the portal deliberately leaves on purchase orders, changes and releases.
- **Exploit:** an administrator once mapped `joe@corp` to the technician while testing. After upgrading, Joe opens My Approvals and approves purchase orders.
- **Fix:** `ApprovalService::isApprovalAccount()` compares the user's ServiceDesk Plus id with the technician's id. The id is looked up by e-mail once and cached per user. A match gives an empty list and `ApprovalNotFound` for view, download and decide, and the attempt is audited.
- **Tests:** `ApprovalServiceGuardsTest`, `IdentityResolverTest`, `MappingManagerTest`.

**S2 – Low – a switched-off module stayed visible from the cache (fixed).**
- Cached approval lists are now filtered by the enabled modules.
- Changing the modules or the technician e-mail clears the cache.
- Opening, downloading and deciding were already blocked.

**S3 – Low – ids with leading zeros could bypass the decision lock (fixed).**
- `SdpClient::id()` now only accepts canonical ids (`^[1-9][0-9]{0,19}$`).
- **Test:** `ApprovalServiceGuardsTest::testIdsWithLeadingZerosAreRefused`.

**S4 – Low – attachment downloads were not rate-limited (fixed).**
- The limit is 200 per user and hour.
- Each download costs 3–5 ServiceDesk Plus calls and up to 30 MB of memory.

**S5 – Low – the release package could be built from a later commit than the tagged one (fixed).**
- The `package` job checks out `github.sha`.

**S6 – Low – other hardening (fixed):**
- quotes are encoded in approval comments;
- Unicode format and bidi characters are removed from download file names;
- e-mail addresses are removed from server texts in the Find Endpoints report;
- the request text kept in the session is cut to the form limits.

**S7 – Low – the 32 MB response cap applies to every call (open).**
- Up to 10 parallel reads could each return 32 MB from a hijacked server.
- Recommendation: a smaller cap for JSON calls, keeping 32 MB only for downloads. It is not changed here because the transport is shared by every call and a wrong cap would break attachments.

**S8 – Low – race conditions (open, documented).**
- `SubmissionGuard` and `RateLimiter` read, then act, without a lock. Parallel POSTs with one token can both pass, so limits can be overshot by about two times.
- Decisions are still protected by `DecisionLock` and the pending re-check.

**S9 – Info – documented, not changed:**
- the audit log has no tamper evidence;
- `DecisionLock` works on one host only;
- uninstall leaves the log file and lock files.

### Verified sound (OWASP Top 10 / ASVS L2)

- **A01 Broken access control:**
  - every admin task needs `checkToken()` and `core.admin`;
  - site tasks need the token, the ACL and a matched identity;
  - ownership is checked against ServiceDesk Plus (requester id, approver id, `loaned_to.id`);
  - no IDOR was found;
  - the inherited `display()` task is refused in every task controller.
- **A02 Cryptographic failures:**
  - AES-256-GCM with a random 96-bit nonce, a 128-bit tag, HKDF-SHA256 and a context bound as associated data;
  - the secret comes from the environment or `configuration.php`, never the database;
  - TLS is verified by default.
- **A03 Injection:**
  - every SQL value is bound;
  - `LIKE` patterns are escaped and `ORDER BY` columns are allow-listed;
  - ServiceDesk Plus criteria are built as arrays, with `requester.id` always the first criterion;
  - templates escape all data, and `HtmlText::toPlain` is used for ServiceDesk Plus HTML.
- **A04 Insecure design:**
  - one-time submission tokens;
  - rate limits;
  - the decision lock;
  - writes are never retried.
- **A05 Security misconfiguration:**
  - CSP with `sandbox`, `nosniff`, CORP and COOP on attachments;
  - only PDF and images are shown inline, after a content check.
- **A06 Vulnerable components:**
  - no Composer packages are shipped;
  - GitHub Actions are pinned to commit SHAs, and Dependabot watches the Actions and the Composer dev tools.
- **A07 Identification and authentication:** the component relies on Joomla login and sessions, and identity is never taken from input.
- **A08 Software and data integrity:**
  - `updates.xml` carries a SHA-256;
  - the build job has read-only access, and publishing runs separately.
- **A09 Logging and monitoring:**
  - audit rows cover decisions, requests, mappings and denials;
  - logs are scrubbed of keys.
- **A10 SSRF:**
  - paths are restricted to `/api/v3` on the configured host;
  - no redirects are followed;
  - HTTP and HTTPS only.

## 8. Explanation of the improvements

Each change is described in the 1.33.0 section of `CHANGELOG.md` and in sections 4–6 above.

**Behaviour changes users may notice:**
- portal users linked to the API technician no longer see approvals;
- more than 200 attachment downloads per hour are refused;
- the log file holds fewer lines unless *Debug System* is on.

**Backward compatibility:** no settings, routes, tables or language keys used by templates were removed. The SQL update only adds an index.

**What the tests cover:**
- **Access control:** guests are not matched; the API technician is refused by e-mail and by id; a switched-off module is refused; an SDP user linked to another Joomla user can't be taken over; a changed e-mail suspends the mapping.
- **Input validation:** API paths outside `/api/v3` and ids that are not canonical are refused; uploads are checked for type, macros, real size and count, and file names are cleaned.
- **API errors:** each ServiceDesk Plus error code maps to its kind; a failed status with HTTP 200 is an error; an HTML page instead of JSON is refused; the key never appears in logs, messages or dumps; reads are retried and writes are not; pages are followed.
- **Encryption:** round trip, a new nonce each time, context binding, a wrong secret or tampering is refused, and the key is never shown when dumped or serialised.
- **Find Endpoints:** only GET requests are sent, and the report holds no names, e-mails, subjects or ids.

**Not executed (missing infrastructure):**
- a Joomla 6 installation, so no end-to-end tests of controllers, views and SQL;
- a live ServiceDesk Plus server, so endpoint shapes and status codes are taken from the code and its references;
- PHPStan or Psalm and PHP_CodeSniffer (not installed, so not run);
- PHP 8.4/8.5 runtime tests.

## 10. Remaining risks and unresolved issues

1. **Accepted by the owner:** new users matched by e-mail are approved automatically (the default). Joomla lets users change their e-mail without verifying it. A user who has never opened the portal can enter the e-mail of a ServiceDesk Plus user who has no portal link yet, and act as that person. To close this, set *Integration Settings → Users → New users* to **Wait for administrator approval**.
2. **API technician e-mail empty:** when no technician e-mail is set, the technician can't be recognised. If it is a shared account, a user could match it by e-mail (see item 1). Setting the e-mail closes this.
3. **Open from sections 5 and 6:**
   - S7: the JSON response cap;
   - S8: race conditions on tokens and rate limits;
   - P2: the approvals scan;
   - P6, P7, P8: sequential reads, `search_fields`, announcements;
   - P10: inline styles under a strict CSP;
   - D6: mappings of deleted users;
   - D7: the access-check refactor.
4. **Not verified against the official documentation or a live server:**
   - the ServiceDesk Plus error codes;
   - the approval add and notification input shapes;
   - `is_service_request` and `approval_status.name` as search fields;
   - the `_uploads` multipart field name;
   - how ServiceDesk Plus renders approval comments and subjects (HTML or text).

## 11. Recommendations

1. **Deleted users:** ship a small user plugin, packaged with the component, that removes the mapping and cache rows on `onUserAfterDelete`. Alternatively, treat a mapping whose Joomla user no longer exists as free.
2. **Approvals scan (P2):** on a test server, confirm that `GET /api/v3/approvals` with `approver.id` returns only that approver's items, even when the list is empty. Then trust an empty answer and skip the scan. Cache the scanned levels per record for all users.
3. **Dashboard reads (P6) and announcements (P8):** send the first page of each status, the counts and the per-announcement reads in one `getMany` round.
4. **Split `ApprovalService`** into a reader and a decider, now that unit tests exist to protect the refactor.
5. **CSP readiness (P10):** draw the bar chart as SVG and use bounded classes for card counts, so a strict `style-src` works.
6. **Static analysis:** add PHPStan level 6 and PHP_CodeSniffer (Joomla standard) to CI.
7. **Smaller JSON cap (S7):** add a per-call response cap (8 MB for API calls, 32 MB for downloads).
8. **Integration tests:** add a Joomla 6 instance in CI (for example `joomla/joomla` in Docker) to test controllers, routes and SQL updates end to end.
