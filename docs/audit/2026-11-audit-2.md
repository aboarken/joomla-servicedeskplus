# Second audit round: com_servicedeskplus 1.33.0 → 1.34.0

Date: 2026-11-24. This report continues `2026-11-audit.md` (1.32.5 → 1.33.0). That report holds the architecture overview and the full OWASP assessment; this one covers what was open after it, what was newly tested, and what changed.

## 1. Executive summary

The first round reviewed the code but could not run it: there was no Joomla site and no ServiceDesk Plus server. In this round the component ran in a real Joomla 6.2.1 site on PostgreSQL, against a stand-in ServiceDesk Plus server that records every call.

- **Installation, upgrade and uninstall work.**
  - 1.33.0 installs from the published package.
  - 1.34.0 installs over it.
  - Uninstall removes every table, file, asset and menu entry.
  - A fresh 1.34.0 install works.
- **55 end-to-end checks pass.** They cover access control, form tokens, other users' records, escaping, approvals, new requests, Find Endpoints and the response size limit.
- **No new Critical, High or Medium security finding.** The end-to-end run confirmed the controls that the first round only read in code.
- **Static analysis** (PHPStan level 5 against the Joomla 6.2.1 source) found no real defect.
- **Eight open items from the first round are fixed.** Four remain open, because fixing them safely needs the owner's real ServiceDesk Plus server.

## 2. Architecture

Unchanged from the first report. One addition: an administrator `Dispatcher` (`administrator/src/Dispatcher/Dispatcher.php`), Joomla's intended place for a component-wide access check. Joomla's `ComponentDispatcherFactory` picks it up by name.

## 3. Findings and status

### Fixed in 1.34.0

| # | From | Finding | Severity | Fix |
|---|---|---|---|---|
| 1 | S8 | Two submissions of one form sent at the same moment could both pass the one-time token, and the hourly limit could be overshot | Low | `DecisionLock::claim()` creates a marker file atomically per token; request creation runs under a per-user lock |
| 2 | S7 | The 32 MB response limit applied to every call, and parallel reads multiplied it | Low | API answers are limited to 16 MB, downloads to 32 MB; an answer that was cut off is not requested again |
| 3 | D7 | The administrator access check was repeated per controller, with no single place | Low | `Dispatcher::checkAccess()` requires `core.admin`; the controller checks stay as a second layer |
| 4 | D6 | The mapping of a deleted Joomla account kept its ServiceDesk Plus user, so a new account of the same person could not be matched | Low | The orphan mapping is removed when that ServiceDesk Plus user is matched or assigned again; never when the account exists or the database cannot say |
| 5 | P8 | Restricted announcements were read one by one | Medium | `SdpClient::getAnnouncements()` reads them in parallel |
| 6 | P10 | `style` attributes for card counts and bar heights break under a strict CSP | Medium | Classes (`sdp-vbars--nN`, `sdp-stats--nN`, `sdp-h-N`) replace them; no `style` attribute is left in any template |
| 7 | new | Parallel reads that timed out were retried (the 1.33.0 fix covered single reads only) | Low | The same rule applies to `getMany()` |
| 8 | front end | Disabled pagination links kept an address and keyboard focus | Low | They are plain text with `aria-disabled` |

### Still open

| # | Finding | Severity | Why it is open |
|---|---|---|---|
| P2 | My Approvals scans every module when the user has nothing pending (15–225 calls on a cache miss) | High (performance) | Trusting an empty answer of `GET /api/v3/approvals` is only safe if the owner's ServiceDesk Plus build honours `approver.id`. Past builds ignored it, so this must be checked on the real server. |
| P6 | Dashboard counts are read one after another | Medium | The fallback logic depends on how the real server answers `is_service_request`; a change needs the real server to confirm. |
| P7 | The user lookup uses the deprecated `search_fields` | Medium | A switch to `search_criteria` on `email_id` must be confirmed on the real server; a wrong guess would stop every sign-in match. |
| F5 | The request subject is sent to ServiceDesk Plus as typed | Info | Whether ServiceDesk Plus shows subjects as text or HTML is not known. Encoding it would show `&lt;` to technicians if it is text. The portal itself escapes subjects. |

**Accepted by the owner (unchanged):** new users matched by e-mail are approved automatically (the default).

## 4. Security assessment of this round

The end-to-end run confirmed in a running system:

- **Administrator:**
  - A guest gets the login form.
  - A Manager without *Configure* is refused.
  - Saving settings, Find Endpoints and the report download all need the form token.
  - The inherited `display` task is a 404.
  - The API key is never sent back to the form.
  - The address cannot be changed without entering the key again.
- **No IDOR:**
  - Another user's request (`view=request&id=300`) and another approver's approval are 404.
  - A forged decision on another approver's approval sends nothing to ServiceDesk Plus.
  - The second user sees only their own records.
- **CSRF:** a decision or a new request without the form token sends nothing to ServiceDesk Plus.
- **XSS:**
  - A subject with markup is escaped.
  - A description with `<script>` is shown as text.
  - An announcement with `onerror` is shown as text.
  - Comments and descriptions go to ServiceDesk Plus with entities.
- **Information disclosure:**
  - Internal notes and technician-only announcements are not shown.
  - The Find Endpoints page and report hold no names, e-mails or request texts.
- **Abuse:**
  - A form sent twice acts once.
  - The hourly limit on new requests holds exactly (3 of 5 attempts with the limit at 3).
  - A 24 MB answer is cut off at 16 MB and the page still works.
- **Integrity of calls:**
  - Every call to ServiceDesk Plus carried the API key.
  - The only writes sent were the decision and the new requests the tests asked for.

Dependencies: no Composer packages are shipped. The development tools (PHPUnit) are watched by Dependabot.

## 5. Functional and business logic findings

- No functional defect was found in the tested workflows: sign-in matching, lists, details, approval decision, new request, loans, announcements, dashboard, Find Endpoints.
- Fixed: the orphan mapping (item 4 above). It was a real functional defect: a person whose account was recreated stayed "ambiguous" until an administrator intervened.
- **Environment note, not a component defect:** on PHP's built-in web server Joomla doubles the path in redirects (`/administrator/administrator/index.php`). Joomla's own core pages do the same there, and setting `$live_site` fixes it. The end-to-end README documents this.

## 6. Database and performance findings

- **Schema:** install, update 1.33.0 → 1.34.0 and uninstall were run on PostgreSQL 16. The schema version in `#__schemas`, the four tables and the audit indexes were verified after each step. No schema change in 1.34.0.
- **MySQL/MariaDB was not available** in the audit environment. The MySQL files mirror the PostgreSQL ones and were reviewed, but not executed.
- **Performance:** announcements are read in parallel (item 5). The remaining items (P2, P6) are listed above.

## 9. Joomla and PHP compatibility

- **Joomla:** tested on 6.2.1. The component uses no deprecated API (checked in the first round and by PHPStan against the 6.2.1 source). The update server offers updates to Joomla 6.x.
- **PHP:** 8.3 is required and tested. No PHP 8.5 deprecation is known in the code (`curl_close()` was removed in 1.33.0), but 8.4 and 8.5 were not run.
- **Databases:** PostgreSQL 16 tested; MySQL/MariaDB reviewed only.

## 10. Recommendations

1. **On the real ServiceDesk Plus server**, check `GET /api/v3/approvals` with `approver.id` (does an approver with nothing pending get an empty list?) and `search_criteria` on `email_id`. With those two answers, P2 and P7 can be fixed safely.
2. **Run the end-to-end tests on MySQL/MariaDB once**, since production sites usually use it.
3. **Add the PHP 8.4/8.5 test jobs** to the workflow.
4. **Split `ApprovalService`** into a reader and a decider, now that unit and end-to-end tests protect the approval flow.
